# Coverage matrix — `invitation`

- **Pattern:** `atoms/invitation.md`
- **Model:** `invitation.tla` (TLA+ state-machine) + two isolated buggy twins — `invitation-buggy.tla` (single-resolution) and `invitation-buggy-derivation.tla` (positive read-time derivation, FC F2); and `invitation.als`, the static data model (+ 13 buggy twins `invitation-buggy-<defect>.als`, 2026-11-11).
- **Reviewer / date:** regenerated 2026-06-23 against the post-refactor model (execution/render-time refactor, 2026-06-21; `now`/`id_t` reverted to pipeline-injected per the Final Critique council, 2026-06-23). Supersedes the 2026-06-03 matrix, which described the pre-refactor model (stored `Expired`, an `Expire` action, four reachable terminal states, no clock variable, and an over-claimed single-resolution-as-concurrency reading).
- **Formal-layer vote load-bearing claims:** Invariant 2 (single-resolution — at most one stored-terminal write, immutable thereafter) and Invariant 12 (expiry is derived, never written — the refactor's load-bearing render-time guarantee).

## Step 0 — model shape (post-refactor)

`Expired` is no longer a stored status. The stored `state` enum is `{Pending, Accepted, Declined, Revoked}`; `Expired` is a **derived read-time projection** (`Lapsed(c) ≜ state = Pending ∧ c ≥ ExpiresAt`, surfaced as `EffStatus(c)`) evaluated against the injected clock `now`. There is no `Expire` action — lapse never writes. The three stored writes are `Accept`, `Decline`, `Revoke`; each guards on `state = Pending ∧ now < ExpiresAt`. A ghost `resolution` records the first stored terminal reached, so single-resolution is the falsifiable predicate `resolution # none ⇒ state = resolution`. The clock and token are pipeline-injected at the I/O seam (not action parameters); the model carries `now` as an advancing clock variable and reads it in the pure resolving guards and in `EffStatus`.

Out-of-scope residual, named: the **concurrent check-and-commit interleaving** (Invariant 2's two-writers-racing-from-Pending atomicity) is verified here only as **post-write immutability** (resolution never changes once set), not as runtime serialization of the check-and-commit window. The atomicity of "read `status = Pending`, then write the terminal" under genuine contention is a **runtime-serialization obligation** — the Execution Contract's sequence-safety class — discharged by the host store (a conditional / compare-and-set write or equivalent serialization), not by the atom's English or this state-machine model. It is recorded here as **by-construction / out-of-scope**, NOT claimed as covered concurrency. (TLA+ interleaving of the two enabled resolving actions does establish *that two actions cannot both win*, since each is disabled once `state ≠ Pending`; what is out-of-scope is the sub-action TOCTOU window between the guard read and the commit write, which is below this model's atomic-action granularity.) Where check-and-commit-under-contention is load-bearing it is a host obligation; composing patterns that serialize onboarding (External Onboarding) inherit it from the contract.

## Step 3 — bound saturation

- **Saturation point: 16 states at `ExpiresAt = 2`, for any `MaxClock ≥ ExpiresAt + 1`.** `Tick` is clamped at `ExpiresAt + 1` (FC F1), so the reachable clock values are `{0, 1, 2, 3}` and exploration saturates there regardless of `MaxClock`. Verified: the model holds at **16 states** for `MaxClock ∈ {3, 6, 10, 20}` — raising the domain bound adds zero reachable states. (Pre-fix, with `Tick` guarded by `MaxClock`, the count grew without bound: 16 → 28 → 44 states at `MaxClock = 3 → 6 → 10`. That unbounded growth was the FC F1 defect; the clamp fixes it.) The 16 states decompose as 4 Pending states (`now ∈ {0,1,2,3}`) + 12 resolved states (3 stored terminals × 4 reachable clock values each). One tick past the deadline (`now = ExpiresAt + 1`) is the only behaviorally-distinct lapsed clock value — every clock value `≥ ExpiresAt` produces identical guard outcomes — so the clamp loses no reachable behavior. The canonical `invitation.cfg` sets `MaxClock = 6` (> the clamp) precisely to demonstrate the headroom adds nothing.

Alloy (2026-11-11): `invitation.als` checks at `for 4 but 5 Invitation` (four calls and four instants: enough for a version four calls deep — initiate, accept, then the decline and the second accept a twin lets through, which `A_Invariant_5_1` needs to tell two terminals apart — and for a resolving write reading two invitations initiated by two calls, which `A_Invariant_11_1` needs; five versions leave room for a branch beside the chain).

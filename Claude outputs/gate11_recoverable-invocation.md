F6 — The walkthrough's `closure_latency` breaches the page's own parts rule, and under its bindings the sweep can never land a closure
  WHERE: *Examples*, Walkthrough bindings; against Configuration §`closure_latency` and §`journal_write_bound`
  DEFECT: Configuration §`closure_latency` states normatively: "`closure_latency` must exceed `read_bound + 2 × journal_write_bound + the probe's round-trip`, since a closure contains one under-section read and two journal writes whatever else it contains. A `closure_latency` below that is a disclosure contradicting the operations it is disclosed over, and the sweep's lease, which is built on it, inherits the contradiction." The walkthrough binds `read_bound = 2 s`, `journal_write_bound = 3 s`, `closure_latency = 5 s`. The floor is `2 + 2×3 = 8 s` plus the probe's round-trip; 5 s is below it. The walkthrough asserts "All four start conditions, shown" — this fifth normative arithmetic obligation is neither shown nor met, and check 4 does not carry it either.
  FAILURE: The sweep's lease is `closure_latency + journal_write_bound = 8 s`. Inside it a closure must spend `read_bound` (2 s) on step 2's under-section re-read, the probe's round-trip, then issue two writes each gated on `remaining ≥ journal_write_bound` and each taking up to 3 s: 2 + p + 3 + 3 = 8 + p. With any probe latency at all, the gate before the outcome write fails, the run "writes nothing more for this act, counts it in `skipped`", and the next run repeats it — writing another `ledger.recovery_intended` each cadence and never a closing. The "The crash" narrative ("The sweep writes `ledger.recovery_intended` then `ledger.disclosed` ... accounted for within about forty seconds") is unreachable under the numbers stated eight lines above it, and every orphan of this deployment breaches its ten-minute window.
  FIX: Raise the walkthrough's `closure_latency` above `read_bound + 2 × journal_write_bound + probe` (e.g. 12 s), re-derive `run_bound` (`3 × (30 + 12) = 126 s`) and re-show the four checks; and add the `closure_latency` parts inequality to the instance-start set that check 4 clears, so the disclosure is checked rather than merely asserted.

REFINING FINDINGS:
R1 — Configuration §`compensation_window`, the headroom obligation · `run_bound ≥ 2 × closure_latency + journal_write_bound` charges the *sweep's* lease as the wait, but §`act_section` and §`run_bound` define the wait as "one holder's remaining lease per act", which for an [Open] holder is `completion_bound` (walkthrough: 30 s vs. the floor's 8 s); the claim that the inequality "breaches on exactly the tuples whose `run_bound` falls below a lease plus a closure" uses the wrong lease → make the floor `max(completion_bound, closure_latency + journal_write_bound) + closure_latency`.
R2 — Configuration §`journal_write_bound`, start check 3 · claimed to be "the act's lease against everything spent under it", but omits the read-backs the position rule mandates — a lost reply requires waiting a full `journal_write_bound` *then* a `read_bound` read *then* a retry, while the write gate only guarantees `journal_write_bound` remaining, so the mandated under-section read-back is reached with `remaining ≈ 0` → charge `3 × read_bound + 3 × journal_write_bound + commit`, or gate writes on `remaining ≥ journal_write_bound + read_bound`.
R3 — Configuration §`read_bound` · enumerates the under-section reads as "[Open] step 3, [Close] step 2, [Refuse] and [Resolve]" and omits [Reconcile] step 2's re-read, which §`closure_latency`'s parts rule charges as `read_bound` → add [Reconcile] step 2 to the enumeration.
R4 — Configuration §`closure_latency` · the parts list ("one under-section read and two journal writes") omits [Resolve]'s `read_record(intent_event_id)` purge check and the derived-index update, though the entry exists so "a disclosure can be checked against them" → name every operation the lease must contain.
R5 — [Resolve] · "gates its write on `remaining ≥ journal_write_bound` as [Close] does" declares a guard with no landing — [Close] step 1 lands `recording-failure(outcome)`, [Resolve] says nothing → state that a failed gate lands `rejected(recording-failure(resolution))` with nothing appended.
R6 — Configuration §`clock_skew_allowance` · "**Six** clocks meet on this page" enumerates six and omits the reader's seam, which *Clock semantics* and [Read Invocation] both declare and which performs the same cross-seam comparisons → say seven and list it, since the deployment sets the allowance "to cover the widest pair".

R8 — Configuration §`act_section` · `try_take` is declared as one of four operations "for keys it examines beyond the ones it must", but no step of [Reconcile] or any other action performs an opportunistic pass; the operation has no caller on the page → either specify the opportunistic pass or drop the operation to three.

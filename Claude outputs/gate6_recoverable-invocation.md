FOUNDATIONAL FINDINGS (most severe first):
F1 — The liveness inequality budgets the dead run with the wrong term [timing]
  WHERE: Configuration `compensation_window`; Invariant 4; Generation acceptance check 4; `run_bound` entry; [Reconcile] step 2
  DEFECT: The inequality `2 × completion_bound + 2 × clock_skew_allowance + reconciliation_cadence + run_bound < compensation_window` counts `completion_bound` twice on the stated ground that "a run that dies holding an act's section holds it until its lease expires, and the next run's take waits exactly that long." But the spec's own `run_bound` entry and [Reconcile] step 2 give the sweep a lease of `max(completion_bound, closure_latency)`, not `completion_bound`, so where `closure_latency > completion_bound` the dead run holds the section longer than the check budgets. The clause also assumes the successor run is already queued at the take; on one node the successor of a run whose process died is the restart run (unbudgeted start), and on two nodes the other node's run arrives up to a cadence after the dead run took the section, so the true second term is `max(reconciliation_cadence, max(completion_bound, closure_latency))`, not `completion_bound + clock_skew_allowance`. A deployment can pass check 4 at start and breach the window on the first orphan with one death — the case the window explicitly claims to cover.
  FAILURE: `completion_bound = 10 s`, `closure_latency = 60 s`, `clock_skew_allowance = 1 s`, `reconciliation_cadence = 60 s`, `run_bound = 120 s`, `compensation_window = 203 s`. Check 4: `20 + 2 + 60 + 120 = 202 < 203`, instance starts. Orphan intent recorded at `t`; examinable at `t + 11`; node A's run starts at `t + 71`, takes the section with lease `max(10, 60) = 60`, dies; section frees at `t + 131`; node B's run (a cadence later) takes at `t + 131` and lands the closing by `t + 251` — 48 s past the window, with no second death.
  FIX: Restate the dead-run term as the sweep's own lease and the successor's arrival — `completion_bound + clock_skew_allowance + reconciliation_cadence + max(reconciliation_cadence, max(completion_bound, closure_latency)) + run_bound < compensation_window` — and either bound restart latency as a Configuration entry or state that a single-node instance's death budget is zero; rewrite the `compensation_window` prose, Invariant 4, check 4, the walkthrough arithmetic and step 5's threshold to match.

F2 — A paused holder's journal write has no fence, so the one-writer claim rests on a check-then-act the spec itself declares insufficient [timing]
  WHERE: Configuration `act_section` ("every journal write after the invocation's first is issued only while `remaining` is at least `journal_write_bound`… so that a write issued inside the lease lands inside it"); Bindings `commit_fence` ("A relative request timeout is not a fence… nothing bounds when a paused process issues one"); Invariant 2 *Rests on*; [Close] steps 1–3; [Reconcile] step 2
  DEFECT: The `commit_fence` binding correctly observes that a lease gate is check-then-act — a process can pass `remaining ≥ journal_write_bound`, pause, and issue its write after the lease has expired — and demands a store-level fence for the bound commit for exactly that reason. The composition's own outcome, refusal, recovery-intended, abandoned and escalated writes are gated by the identical check-then-act against `remaining`, and `AuditTrail.record_action` carries no deadline parameter and no fence; nothing in the substrate's contract stops a write issued after expiry from landing. Invariant 2's "never both" therefore does not hold under the pause the spec admits, and [Close] step 2's proceed-as-landed (also a read-then-write under the same lease) does not close it. Check 2 names the consequence `binding-duplicate` but no section says which of two outcomes a reader or the sweep treats as the act's.
  FAILURE: Invocation I holds the section (`completion_bound = 30 s`, `journal_write_bound = 5 s`). At `remaining = 6 s` [Close] passes step 1 and step 2's pre-check; the process is paused (GC, VM migration) for 10 s; the lease expires; the sweep takes the section, re-reads (nothing), probes `committed`, writes `recovery_intended` and the outcome, releases. I resumes and issues its `record_action` for the outcome; the substrate accepts it. Two outcome records name I's `invocation_id`.
  FIX: Either declare a `journal_fence` instance capability on the substrate's Event Log (a request-scoped deadline the host attaches to every `record_action` this instance issues, judged on the substrate's clock under `clock_skew_allowance`, with the sweep's examine edge widened by one more allowance as the store fence already is), or admit the residual explicitly: state that Invariant 2 holds modulo an unfenced pause, and give check 2 and [Read Invocation] a deterministic rule (lowest `sequence_number` wins; the later record is a surfaced `binding-duplicate`, not a second act).

F3 — The read-your-writes requirement is bounded by time-since-issue, but the handoff on release reads before that bound has elapsed [timing]
  WHERE: Composes, *Instance capability requirements* ("a record this instance appended is visible to its next range read once `journal_write_bound` has elapsed since the append was issued"); Configuration `act_section` ("released on the holder's return… two waiters are admitted in the order they arrived"); [Reconcile] step 2 ("because every write issued inside a lease lands inside it, the next run's re-read sees everything this run landed"); [Open] step 4 and [Close] step 3 read-backs after a received `invalid-request`
  DEFECT: The only visibility guarantee this composition declares over the substrate is time-based: a record is visible once `journal_write_bound` has elapsed since issue. Every argument for why a second writer's re-read is sufficient names lease *expiry* — but the common path is release-on-return, which frees the section the instant `record_action` returns, typically well inside `journal_write_bound`. A queued waiter is admitted at that instant and re-reads immediately; the declared requirement does not promise it sees the write. The same gap applies to [Open] step 4's and [Close] step 3's read-back after a received `invalid-request` (the reply arrived; nothing says the append is yet visible). The spec says of itself that "a miss here is followed by a retry that appends the duplicate Invariant 2 forbids" — and the declared capability does not cover the path.
  FAILURE: Two nodes, both sweeping act K past the edge. Run A takes K, probes `committed`, writes the outcome (`record_action` returns 300 ms after issue; `journal_write_bound = 5 s`), releases. Run B, queued on the take, is admitted at once and re-reads `open_invocations[K]` and `closed_acts` from a replica the requirement permits to lag another 4.7 s; it sees no closing, probes `committed`, writes a second `recovery_intended` and a second outcome. `binding-duplicate` at quiescence.
  FIX: Restate the requirement against the event the protocol actually waits on: a record whose `record_action` has *returned* (any arm that leaves it appended) is visible to every subsequent range read of the instance from any node, and a record whose reply was lost is visible once `journal_write_bound` has elapsed since issue; then delete the lease-expiry justification in [Reconcile] step 2 or make it the second of two grounds.
